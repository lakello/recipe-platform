# AGENTS.md

## Обзор проекта

Recipe Platform — полноценное приложение с DevOps-подходом. Компоненты: бэкенд на FastAPI, фронтенд на React/TypeScript, десктопное приложение на Tauri, Android-приложение на Kotlin/Jetpack Compose, инфраструктура в Yandex Cloud (Terraform + Ansible + Kubernetes/Helm).

**Статус**: приложение и часть Terraform-инфраструктуры реализованы. Android, Desktop, CI/CD, Kubernetes/Helm и Ansible ещё не реализованы.

## Контекст директорий

В каждой основной директории проекта есть `README.md`. Перед началом работы с директорией — читать её README, чтобы понять текущее состояние и назначение директории.

## Локальная разработка

Полный стек запускается через Docker Compose из корня проекта (бэкенд, фронтенд, Postgres, Redis, OpenSearch, MinIO, Mailhog, Celery worker + beat).

Примеры переменных окружения находятся в корне проекта, `backend/` и `frontend/`. Локальные `.env`-файлы с реальными значениями должны оставаться в `.gitignore`.

## Команды сборки и тестирования

### Бэкенд (Python 3.12, FastAPI)
```bash
cd backend
ruff check .                                           # линтинг
ruff format .                                          # форматирование
mypy app                                               # проверка типов
pytest                                                 # тесты
alembic upgrade head                                   # применить миграции (перед запуском сервера)
uvicorn app.main:app --reload                          # dev-сервер
alembic revision --autogenerate -m "describe change"  # создать миграцию
```

### Фронтенд (React, TypeScript, Vite)
```bash
cd frontend
npm run lint        # линтинг (ESLint)
npm run typecheck   # проверка типов
npm run dev         # dev-сервер
npm run build       # production-сборка
```

Автоматические frontend-тесты пока не настроены.

### Инфраструктура
```bash
cd infra/terraform && terraform fmt && terraform validate
cd infra/helm && helm lint . && helm template .
ansible-lint        # линтинг Ansible-плейбуков
```

## Git-воркфлоу

Полная стратегия ветвления и правила PR описаны в `CONTRIBUTING.md`.

Ключевые правила:
- Прямые пуши в `main` и `develop` запрещены
- `feature/*` — создаётся от `develop`, вливается в `develop`
- `release/*` — создаётся от `develop`, вливается в `main`, затем обратно в `develop`
- `hotfix/*` — создаётся от `main`, вливается в `main` + `develop` + активный `release/*`
- PR требует прохождения всех CI-проверок; деплой в production требует ручного подтверждения
- После merge ветку нужно удалить (`git branch -d` + `git push origin --delete`)

## Формат коммитов

Conventional Commits: `<type>(scope): <description>`

Типы: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `ci`, `infra`, `build`

```
feat(auth): add google oauth callback
fix(recipes): validate uploaded image mime type
infra(terraform): add managed redis module
ci: add pull request workflow
```

## Политика секретов

Никогда не коммитить секреты. Запрещено: пароли, JWT-секреты, OAuth-credentials, DB/Redis/S3/SMTP-учётные данные, kubeconfig, Terraform-credentials, `.env`-файлы с реальными значениями.

Использовать: GitHub Actions Secrets, Yandex Lockbox, Kubernetes Secrets, External Secrets Operator или локальные `.env` (в `.gitignore`).

## Тегирование Docker-образов

Production-образы должны использовать иммутабельные теги (git SHA или semver — например, `v1.2.0`, `sha-abc1234`). Тег `latest` в production запрещён.

## Требования к PR

Заголовок PR — в формате Conventional Commits. Описание должно включать: суть изменений, ссылку на задачу (если есть), затронутые компоненты, отсутствие секретов. Все CI-проверки должны пройти до merge.

## Процесс выполнения задач

Проект используется для изучения DevOps. Задачи делятся на два типа в зависимости от технологии.

### Что считается DevOps-задачей

Технологии, которые выполняет **пользователь**: Docker, Nginx, Kubernetes, CI/CD, Terraform, Ansible, сетевые настройки (networking), облачные сервисы (Yandex Cloud и др.), Linux.

Git — выполняет **Агент** (пользователь уже знает его как разработчик; делегирование ускоряет процесс).

### Не-DevOps задачи (бэкенд, фронтенд, конфигурация приложения и т.д.)

Claude выполняет самостоятельно, без участия пользователя.

### DevOps-задачи — процесс

Строгий порядок:

1. **Изучить проект** — перед постановкой шага Агент проверяет код, конфигурацию, README и историю текущих изменений, чтобы выяснить, делалось ли в проекте что-то аналогичное. Нельзя предлагать новый подход, не проверив существующие примеры и соглашения.
2. **Если аналог уже есть** - переиспользовать существующий подход. Агент указывает пользователю точные файлы и фрагменты, объясняет связь с текущей задачей и кратко объясняет концепцию (что это такое и зачем), чтобы у пользователя было базовое представление. Прямых инструкций не давать. Агент переходит к шагу 5.
3. **Если аналога нет** - объяснить новую концепцию, Агент сначала простыми словами объясняет, что требуется, зачем это нужно и какую проблему решает.
4. **Дать конкретное задание** — Агент прямо и последовательно говорит, что и где пользователь должен изменить: называет файлы, ресурсы, параметры, связи и ожидаемый результат. Каждый существенный шаг сопровождается объяснением, зачем он нужен и почему выбран именно такой вариант. Инструкции должны быть достаточно полными, чтобы пользователь мог изучить их и выполнить ровно описанные действия без догадок.
5. **Выполнить** — пользователь самостоятельно вносит изменения по этим инструкциям.
6. **Проверить** — Агент проверяет результат инструментами (Read, Bash), а не принимает его на слово.
7. **Исправить или продолжить** — если есть ошибки, Агент точно указывает место, причину и требуемое исправление; к следующему шагу переходить только после успешной инструментальной проверки.

Правила подсказок:
- Не заставлять пользователя угадывать следующий шаг и не выдавать намеренно неполные инструкции.
- По умолчанию давать конкретный план изменений с пояснением причин, но не вносить DevOps-изменения вместо пользователя.
- Если пользователь просит уточнение, раскрывать детали нужного файла, ресурса или параметра ещё конкретнее.
- Готовый результат не подменяет обучение: пользователь должен понимать назначение каждого выполняемого изменения.

Общие правила:
- Никогда не пропускать шаги и не переходить вперёд без явного подтверждения текущего.
- Если пользователь не понимает что-то — объяснять простым языком, без лишнего жаргона.
- Если шаг сложный — разбить его на подшаги.
- **Git-операции (коммиты, ветки, stash) выполняет Агент**, а не пользователь. Соблюдать стратегию ветвления из `CONTRIBUTING.md`: feature-ветки создаются от `develop`, коммиты — в формате Conventional Commits.

### Вопросы и предложения

Агент может и должен задавать вопросы и давать предложения — как в ходе выполнения задач, так и перед изменением правил работы. Если есть сомнения в подходе, лучшее решение, или что-то важное для уточнения — сначала спросить/предложить, обсудить, и только потом действовать.

## Работа с задачами в WEEEK

WEEEK — основной источник состояния и прогресса задач проекта.

### Доступ к API

- Использовать WEEEK Public API: `https://api.weeek.net/public/v1`.
- Токен брать только из переменной окружения `WEEEK_API_TOKEN`.
- Никогда не просить пользователя прислать токен в чат, если переменная отсутствует. Попросить настроить переменную и перезапустить Codex.
- Никогда не выводить значение токена, не сохранять его в репозитории, `.env`, документации, скриптах или логах.
- Проект WEEEK: `RecipeMeal Planner`, Project ID `9`.
- Доску `Архив` не изменять без отдельного явного указания пользователя.

### Жизненный цикл задачи

1. Перед началом получить актуальные доски, колонки, задачу и её подзадачи через API.
2. Найти задачу по ID или точному названию и убедиться, что выбрана правильная доска. Не определять задачу только по похожему названию.
3. Когда основная задача фактически взята в работу, переместить её в колонку `В работе` и запустить на ней таймер. Простое чтение или оценка задачи не считается началом работы.
   - Пока работа над задачей продолжается, таймер должен оставаться запущенным, в том числе когда пользователь самостоятельно выполняет шаг, отвечает на вопрос, исправляет найденную ошибку или ожидается его результат для проверки.
   - Не останавливать таймер только потому, что текущий ход передан пользователю.
   - Останавливать таймер только при полном завершении основной задачи или при реальной паузе, когда работа над ней фактически прекращена: пользователь явно поставил задачу на паузу, команда переключилась на другую задачу либо возникла внешняя блокировка без продолжающихся действий.
4. Выполнять подзадачи по очереди. После фактического выполнения и инструментальной проверки каждой подзадачи сразу отмечать её выполненной в WEEEK.
5. Если проверка не прошла или работа заблокирована, не отмечать подзадачу выполненной. Основную задачу оставить в колонке `В работе`.
6. Основную задачу можно завершить только когда:
   - выполнены все её обязательные подзадачи;
   - пройдены необходимые тесты, линтеры и другие проверки;
   - для DevOps-задачи результат проверен инструментами;
   - выполнено требуемое ручное тестирование пользователя.
7. Когда основная задача полностью готова, остановить на ней таймер, отметить её выполненной и переместить в колонку `Готово`.
8. После каждого изменения повторно прочитать задачу через API и убедиться, что изменены правильные ID, `parentId`, колонка и состояние выполнения.

Если у основной задачи нет подзадач, применяется тот же процесс: `В работе` → выполнение → проверка → отметить выполненной → `Готово`.

### Правила синхронизации

- Не сбрасывать существующие статусы, исполнителей, сроки и колонки.
- Не создавать дубликат, пока не проверены все задачи проекта с пагинацией.
- Новые подзадачи создавать с `parentId` основной задачи и не размещать их отдельно на доске.
- Критерии готовности хранить в описании основной задачи, а выполняемые действия — в подзадачах.
- Не отмечать задачу выполненной только на основании сообщения пользователя — сначала проверить результат доступными инструментами.
- Массовое удаление задач, удаление досок и изменение завершённых этапов выполнять только по отдельному явному запросу.

## Требования к созданию PR

PR создаётся **только после подтверждения**, что всё работает:

1. Реализация завершена, тесты проходят, линтинг чист.
2. Пользователь протестировал вручную и подтвердил, что всё работает корректно.
3. Если найдены баги — фиксим их (коммиты в ту же ветку), возвращаемся к п. 2.
4. Только после явного «всё ок» от пользователя — создаём PR.

**Никогда не создавать PR сразу после реализации**, не дождавшись ручного тестирования.

## Актуализация README после задачи

После успешного слияния feature-ветки в `develop` — **автоматически** создать ветку `docs/update-readme-<название-задачи>` от `develop` и выполнить следующее:

1. Проверить README-файлы во всех директориях, которых коснулись изменения задачи.
2. Актуализировать те, что устарели — README должен описывать **что есть сейчас** в директории и зачем она нужна. Если README уже актуален, не трогать.
3. Проверить и при необходимости обновить корневой `README.md`.
4. Сделать коммит и PR в `develop`.

Цель README — описать текущее состояние директории, а не планы. Не переписывать разделы о будущем — только актуализировать то, что уже изменилось.
